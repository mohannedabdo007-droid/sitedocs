# SiteDocs — تدقيق RLS وStorage وفصل صلاحيات سير العمل
**التاريخ:** 2026-11-14  
**الفرع:** `fix/cloudflare-workers-build-2026-11-13`  
**المشروع المستهدف:** `jezpyxuxjzxotxjykhky`  
**نوع الفحص:** مراجعة ثابتة لملفات migrations + محاولة فحص حي للـ Supabase  
**الحالة:** ثغرات/مخالفات مؤكدة في مصدر migrations؛ الحالة الفعلية المنشورة لم تُثبت بسبب رفض صلاحية الاتصال.

## 1. نتيجة الوصول إلى قاعدة البيانات الحية

تمت محاولة قراءة المشروع والجداول وmigrations وSecurity Advisors باستخدام موصل Supabase على المشروع الصحيح. جميع عمليات القراءة أعادت:
`MCP error -32600: You do not have permission to perform this action`.

لم أكرر المحاولة بعد ثبوت أن صلاحيات الاتصال الحالية لا تسمح بها. لذلك:
- لا أدّعي أن السياسات الموجودة في migrations هي بالضرورة السياسات المنشورة حالياً.
- لا أدّعي أن قاعدة البيانات أو Storage تم فحصهما مباشرة.
- لم أنفذ SQL، ولم أعدل أي سياسة أو bucket أو جدول أو دالة.
- يلزم لاحقاً منح موصل Supabase صلاحية قراءة Metadata/Database للمشروع المحدد فقط، ثم إعادة جرد `pg_policies` وACL وتعريفات الدوال وStorage buckets/policies.

## 2. النتائج المؤكدة من مصدر المشروع

### P0-1 — المسودات مكشوفة على مستوى RLS في migration المصدر

**الملف:** `drizzle/migrations/0000_core_schema.sql`

السياسة الحالية في المصدر:

```sql
create policy "documents: members read" on public.documents
for select to authenticated
using (public.is_project_member(project_id));
```

لا يوجد شرط على `status` أو `created_by` أو party أو صلاحية إشرافية مستقلة. وبالتالي تسمح السياسة المصدرية لكل عضو مشروع بقراءة صف المسودة.

المشكلة تمتد إلى:
- `document_revisions`: القراءة لكل أعضاء المشروع.
- `document_reviews`: القراءة لكل أعضاء المشروع.
- `attachments`: القراءة لكل أعضاء المشروع.
- `audit_log`: قراءة أحداث المشروع لكل أعضاء المشروع دون تطبيق صلاحية رؤية الوثيقة الأصلية.

**القرار الوظيفي الذي يجب فرضه:** منشئ المسودة يقرأ مسودته؛ مدير المشروع يقرأ جميع المسودات للإشراف فقط؛ الأطراف الأخرى لا ترى المسودة قبل الإرسال الرسمي. قراءة مدير المشروع لا تمنحه تعديل أو إرسال أو مراجعة أو اعتماد.

### P0-2 — سجل التدقيق يعيد فتح مسار كشف المسودة

**الملف:** `drizzle/migrations/0001_triggers_and_rpcs.sql`

الدالة `audit_row()` تستخدم `to_jsonb(new)` وتضع الصف كاملاً في `changes` عند INSERT. ويُنشأ trigger على `documents`.

هذا يعني أن حدث إنشاء المسودة قد يحتوي عنوانها ووصفها وmetadata وحقولاً أخرى، بينما سياسة قراءة `audit_log` تسمح لكل عضو مشروع بقراءة أحداث المشروع.

إخفاء صف الوثيقة وحده لا يغلق هذا المسار. يلزم تقليل payload إلى allowlist، وربط قراءة الحدث بصلاحية قراءة الوثيقة، وعدم تخزين محتوى حساس غير مطلوب في سجل مشترك.

### P0-3 — صلاحية مدير المشروع متداخلة مع صلاحية تعديل المستندات

**الملف:** `drizzle/migrations/0000_core_schema.sql`

`project_role_of()` يعيد `admin` لمدير/مالك الشركة حتى لو لم يكن له تعيين طرف مستقل في `project_members`.

ثم:
- `can_edit_documents()` يسمح لـ `admin` و`controller`.
- `can_comment()` يسمح لـ `admin` و`controller` و`reviewer`.
- `can_manage_project()` يسمح لـ `admin`.

هذا لا يطابق قرار أن مدير المشروع يملك قراءة إشرافية للمسودات ولا يكتسب تلقائياً صلاحية تعديلها أو مراجعتها أو اعتمادها. كما يجعل دور الشركة الإداري يتحول تلقائياً إلى دور مشروع إداري واسع.

**المعالجة المطلوبة:** فصل الصلاحيات إلى قدرات مستقلة: `can_read_all_drafts`، `can_edit_documents`، `can_submit_documents`، `can_review_current_step`، `can_manage_project_config`. لا يجوز استنتاج صلاحية سير عمل من صفة admin العامة.

### P0-4 — RPC سير العمل يتجاوز مطابقة الطرف ويغيب عنه منع الاعتماد الذاتي

**الملف:** `drizzle/migrations/0001_triggers_and_rpcs.sql`

في `transition_document()`:
- `submit` يتجاوز مطابقة الطرف إذا كان الدور `admin`.
- `start_review` يتجاوز مطابقة الطرف إذا كان الدور `admin`.
- `respond/return` يتجاوز مطابقة الطرف إذا كان الدور `admin`.
- لا يوجد فحص صريح يمنع `auth.uid() = documents.created_by` من تسجيل قرار مراجعة على الوثيقة نفسها.

هذه مخالفة مباشرة لفصل الصلاحيات المعتمد. لا يجوز لمدير المشروع أو مدير الشركة أن يحل محل طرف سير العمل تلقائياً، ولا يجوز لمنشئ الوثيقة اعتمادها بنفسه.

### P0-5 — Storage SELECT أوسع من صلاحية الوثيقة والمرفق

**الملف:** `drizzle/migrations/0002_storage_policies.sql`

السياسة المصدرية:

```sql
create policy "document files: project members read"
on storage.objects for select to authenticated
using (
  bucket_id = 'document-files'
  and public.is_project_member(public.storage_project_id(name))
);
```

القراءة تعتمد على أول جزء من مسار الملف بوصفه project UUID وعضوية المشروع فقط. ولا تتحقق من:
- وجود صف مطابق في `public.attachments`.
- ربط `storage_path` بالمرفق والوثيقة.
- حالة الوثيقة ومسودة/مرسلة.
- صلاحية الطرف الحالي في رؤية الوثيقة.
- اتساق company/project/document.
- كون المرفق ما زال فعالاً وغير orphaned.

سياسة INSERT تسمح للمستخدم الذي يمر من `can_comment` برفع ملف تحت مسار المشروع. صلاحية الرفع ليست بديلاً عن صلاحية القراءة.

**المعالجة المطلوبة:** ربط قراءة كل object بصف attachment canonical وبالوثيقة وصلاحية رؤيتها. يجب أن تفشل القراءة إذا لم يوجد المرفق أو كان المسار أو الشركة أو المشروع غير متطابق. لا نعتبر إخفاء المرفق في الواجهة حماية لملف Storage.

### P1-6 — ACL لدوال SECURITY DEFINER يحتاج تدقيقاً شاملاً

المصدر ينشئ عدة دوال `SECURITY DEFINER` داخل `public`. بعض الدوال يسحب EXECUTE من `anon` فقط، وبعضها لا يظهر له سحب صريح. لا يظهر في migration المعاين سحب شامل من `PUBLIC` يتبعه GRANT محدد للأدوار المطلوبة لكل دالة.

PostgreSQL يمنح EXECUTE إلى `PUBLIC` افتراضياً عند إنشاء الدالة ما لم تُضبط default privileges أو ACL خلاف ذلك. لا يمكن الجزم بالوضع الفعلي دون قراءة `pg_proc.proacl` وdefault privileges في قاعدة المشروع.

**المعالجة المطلوبة:** جرد ACL لكل دالة، ثم revoke من PUBLIC/anon حيث يلزم، وإعادة grant لأقل دور يحتاجها. لا نسحب EXECUTE من helpers التي تعتمد عليها سياسات RLS قبل تحديد الاعتماديات واختبارها.

## 3. ترتيب المعالجة المقترح

1. إغلاق قراءة المسودات عبر الوثائق والمراجعات والإصدارات والمرفقات وسجل التدقيق في سياسة موحدة.
2. فصل صلاحية مدير المشروع للقراءة الإشرافية عن التعديل وإجراءات سير العمل.
3. إزالة تجاوز admin لمطابقة طرف سير العمل ومنع اعتماد المنشئ لنفسه داخل RPC.
4. ربط Storage object بصف attachment والوثيقة وصلاحية رؤيتها، ثم تحديد سلوك signed URLs.
5. تقليل بيانات audit payload وربط كل حدث بسياسة رؤية الكيان الأصلي.
6. جرد EXECUTE ACL وdefault privileges لجميع دوال SECURITY DEFINER.

## 4. اختبارات القبول الإلزامية قبل أي تطبيق

| الحالة | المتوقع |
|---|---|
| منشئ المسودة يقرأ مسودته | سماح |
| مدير المشروع يقرأ مسودة للإشراف | سماح قراءة فقط |
| طرف آخر يقرأ مسودة قبل الإرسال | رفض |
| طرف آخر يحاول قراءة revision/review/audit لذات المسودة | رفض أي محتوى يكشف المسودة |
| مدير المشروع يحاول تعديل المسودة | رفض ما لم يكن له تفويض مستقل معتمد |
| مدير المشروع يحاول submit/respond/approve بصفته admin فقط | رفض |
| منشئ الوثيقة يحاول اعتماد وثيقته | رفض |
| المراجع المعين للطرف والخطوة الحالية يرد على الوثيقة | سماح |
| عضو مشروع يطلب object لا يقابله attachment | رفض |
| عضو مشروع يطلب ملف مسودة لا يحق له قراءتها | رفض |
| object بمسار لا يطابق attachment/project/company/document | رفض |
| مستخدم من مشروع آخر يطلب الملف | رفض |
| دور يرفع ملفاً ولا يملك قراءته | الرفع والقراءة يحكمان كلٌ على حدة |
| مستخدم غير مخول يستدعي SECURITY DEFINER RPC | رفض من ACL أو تحقق الدالة |

يجب تنفيذ الاختبارات على قاعدة معزولة مستعادة، وبجلسات JWT حقيقية لكل دور/طرف، واختبار PostgREST وStorage مباشرة لا عبر الواجهة فقط.

## 5. بوابة التنفيذ

لا يتم تطبيق تغييرات قاعدة البيانات قبل:
1. قراءة الحالة الحية الفعلية بعد إصلاح صلاحية موصل Supabase.
2. نسخة احتياطية مستقلة وإثبات نجاح استعادتها.
3. إعداد migration صغيرة مع اختبارات سلبية وإيجابية على بيئة معزولة.
4. مراجعة ACL وSecurity Advisors بعد التغيير.
5. موافقة صريحة على تطبيق migration على قاعدة البيانات المستهدفة.

**الحالة الحالية:** تدقيق المصدر وتحديد العيوب مكتملان؛ التحقق الحي blocked بسبب صلاحية موصل Supabase؛ لا توجد تغييرات على DB أو Storage أو migrations أو الإنتاج.
