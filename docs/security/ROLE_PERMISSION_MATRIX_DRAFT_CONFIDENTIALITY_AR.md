# SiteDocs — مصفوفة الصلاحيات وسرية المسودات
**الحالة:** أساس تنفيذ P0؛ حقل مدير المشروع وفصل صلاحيات الشركة/المشروع ممثلان في migration مرشحة على فرع التطوير، ولم يُثبت التنفيذ على قاعدة معزولة بعد.  
**الفرع:** `fix/cloudflare-workers-build-2026-11-13`  
**مرجع البداية:** `0b20a9325a23db9e05e7d324f8a225b1f11250e1`  
**التاريخ:** 2026-11-15

## 1. الغرض والنطاق

تحدد هذه المصفوفة حدود الصلاحيات بين: منشئ الوثيقة، المراجع المكلف، مدير المشروع، ومدير الشركة. وهي مرجع إعداد اختبارات P0-1 (سرية المسودات) وP0-2 (منع تسريب بيانات المسودات عبر سجل التدقيق).

هذه المصفوفة لا تمنح أي دور صلاحيات لمجرد المسمى الوظيفي. الصلاحية تُمنح على مورد محدد وفي سياق المشروع وحالة الوثيقة والطرف والخطوة الحالية، ويعاد التحقق منها في قاعدة البيانات/RPC/Storage وليس في الواجهة فقط.

## 2. المصطلحات وحدود الأدوار

- **منشئ الوثيقة (Creator/Originator):** المستخدم الذي يطابق `documents.created_by`، وينشئ المسودة نيابة عن `originator_party`. إنشاء الوثيقة أو ملكية المسودة لا يمنح حق مراجعتها أو اعتمادها.
- **المراجع (Reviewer):** مستخدم له عضوية مشروع وطرف `project_members.party` يطابق الطرف الحالي في `workflow_steps[current_step]`، ومكلف فعلياً بالمراجعة. دور `project_role='reviewer'` وحده لا يكفي إذا لم يكن الطرف/الخطوة الحالية مطابقين.
- **مدير المشروع (Project Manager):** دور إشرافي للقراءة فقط. يجوز له الاطلاع على جميع المسودات في مشروعه لأغراض الإشراف. لا تمنحه هذه الرؤية حق تعديل الوثيقة أو تقديمها أو التعليق عليها بصفة مراجعة أو تنفيذ انتقال في سير العمل أو اعتمادها.
- **مدير الشركة (Company Owner/Admin):** عضوية شركة ذات `company_members.role IN ('owner','admin')`. هذه صفة إدارة شركة وليست تفويضاً تلقائياً لمراجعة وثائق المشروع أو تجاوز طرف سير العمل. أي صلاحية إدارية على مشروع أو وثيقة يجب أن تكون منفصلة وصريحة ومحددة.

## 4. قواعد سرية المسودات (P0-1)

1. المسودة مرئية لمنشئها وأعضاء الطرف المنشئ (originator_party) داخل المشروع، ولمدير المشروع المعين صراحةً بصفة إشرافية، ولخدمات النظام الموثوقة اللازمة لتنفيذ العمليات. عضوية الشركة وحدها لا تمنح حق الرؤية.
2. بقية أعضاء المشروع، بما فيهم المراجع الذي لم تبدأ مهمته بعد، لا يرون المسودة أو محتواها قبل التقديم الرسمي.
3. بعد التقديم، يرى الوثيقة الطرف المنشئ والطرف المكلف بالخطوة الحالية فقط؛ بعد الإغلاق، ترى الأطراف الموجودة في مسار workflow. لا تتحول الوثيقة إلى مورد عام لكل أعضاء المشروع.
4. نفس قرار الرؤية يحكم الوثيقة وإصداراتها ومراجعاتها وتعليقاتها ومرفقاتها وStorage وOCR والتقارير وRPC. كما أن دفعات الاستيراد وصفوفها وسجلها لا تظهر إلا لمنشئ الدفعة أو مدير مشروع ذي صلاحية إدارة صريحة.
5. قراءة مدير المشروع للمسودة لا تمنحه أي كتابة أو تقديم أو مراجعة أو اعتماد.
6. لا يجوز الاعتماد الذاتي: منشئ الوثيقة لا يصدر قرار مراجعة/اعتماد على الوثيقة نفسها، حتى لو امتلك عضوية أخرى أو صفة إدارية متزامنة. الإجراء الحالي يمنع نفس المستخدم؛ أما الفصل على مستوى الشركة/الجهة فيحتاج قراراً مستقلاً.

## 5. قواعد سجل التدقيق (P0-2)

1. كل حدث يحمل `document_id` يجب أن يخضع لنفس قرار رؤية الوثيقة الأصلية؛ لا تكفي عضوية المشروع وحدها.
2. حدث المسودة لا يجوز أن يعيد كشف عنوانها أو وصفها أو metadata أو بيانات المرفقات أو أي محتوى محمي لمن لا يستطيع قراءة الوثيقة.
3. يجب تقليل `changes` إلى allowlist من حقول التدقيق الضرورية. يمنع تسجيل الصف كاملاً عبر `to_jsonb(NEW)` أو `to_jsonb(OLD)` في أحداث الوثائق دون تنقية.
4. يجب منع تسريب المحتوى عبر `entity_type/entity_id` أو الحقول النصية أو بيانات التغييرات أو أحداث الكيانات التابعة.
5. أحداث الشركة/المشروع غير المرتبطة بوثيقة تخضع لصلاحية مستقلة محددة، ولا يجوز استعمال صلاحية مدير الشركة لقراءة أحداث وثيقة محمية.
6. لا تمنح صلاحية قراءة سجل التدقيق أي صلاحية تعديل على المورد الأصلي.

## 6. ربط المصفوفة بالـ schema الحالي — فجوات يجب إغلاقها

المصدر الحالي يعرف:
- `company_role`: owner/admin/member.
- `project_role`: admin/controller/reviewer/viewer.
- `project_party`: contractor/consultant/owner/pmc.
- `documents.created_by`, `originator_party`, `status`, `workflow_steps`, `current_step`.
- أضافت migration المرشحة `project_members.is_project_manager` كتعيين إشرافي صريح مستقل عن `project_role`؛ لا يُستنتج من `viewer` أو `party='pmc'`، ولا يمنح أي صلاحية كتابة أو انتقال سير عمل.

الفجوات:
1. لا يجوز افتراض أن `project_role='viewer'` يعني مدير المشروع؛ ولا أن `party='pmc'` تعني تلقائياً مدير المشروع. التعيين الإشرافي الصريح يتم عبر `project_members.is_project_manager=true`، ويظل منفصلاً عن صلاحيات التعديل.
2. migration المرشحة تستبدل `project_role_of()` لتقرأ عضوية المشروع الصريحة فقط؛ عضوية مالك/مدير الشركة لا تنشئ `admin` مشروعياً. من ينشئ مشروعاً عبر `create_project()` يحصل على عضوية مشروع admin صريحة في لحظة الإنشاء.
3. migration المرشحة تفصل صلاحيات المشروع العامة عن `can_edit_document()` و`can_attach_document()` و`can_comment_document()` و`can_create_document()` المرتبطة بالوثيقة والطرف والحالة؛ كما تربط OCR ودفعات الاستيراد بحدود المورد.
4. migration `0004_p0_draft_confidentiality_and_audit.sql` تضيف `can_read_document()` وتربط بها RLS للوثائق والمراجعات والإصدارات والتعليقات والمرفقات وStorage وسجل التدقيق، وتضيف allowlist مستقلة لحقول audit.
5. RPC `transition_document()` المرشح يتحقق من هوية المنشئ عند التقديم، ومن الطرف الحالي عند المراجعة، ومن الطرف النهائي عند الإغلاق؛ ولا يمنح admin تجاوزاً عاماً للطرف.

## 7. مسائل غير محسومة — لا تُفترض في التنفيذ

- يتيح الحقل الحالي تعيين أكثر من مدير مشروع إشرافي صراحةً؛ إذا كان المنتج يشترط مديراً واحداً فقط، يلزم قيد uniqueness/آلية نقل تكليف بقرار وظيفي مستقل. التعيين يتم من إدارة المشروع ذات الصلاحية الصريحة.
- قاعدة التنفيذ الحالية: المراجع لا يرى الوثيقة قبل وصولها إلى خطوته؛ بعد التقديم يرى الطرف المنشئ والطرف الحالي، وبعد الإغلاق ترى أطراف مسار workflow.
- هل فصل الاعتماد الذاتي يقتصر على `auth.uid() = created_by` أم يمتد إلى نفس الشركة/الجهة؟ القاعدة الآمنة المؤقتة: منع نفس المستخدم قطعياً، وحجب حالات تداخل العضويات الملتبسة إلى أن يعتمد حد الجهة.
- ما صلاحيات إدارة المشروع المسموح بها لمدير الشركة تحديداً؟ لا تُستنتج من owner/admin.
- ما حقول audit المسموح الاحتفاظ بها لكل نوع كيان؟ يجب تحديد allowlist تقنية قبل تقليل payload، مع المحافظة على سجل غير قابل للتلاعب.

## 8. بوابة الانتقال

أُعدت migration مرشحة وملفات اختبار على فرع التطوير فقط. لا تُطبق على قاعدة SiteDocs الحية. يجب تطبيقها على قاعدة معزولة وتشغيل حالات السماح والمنع وStorage وRPC وACL قبل اعتبار أي P0 مغلقاً. لا SQL على قاعدة SiteDocs الحية، ولا Storage حي، ولا نشر، ولا دمج إلى main ضمن هذه المرحلة.
