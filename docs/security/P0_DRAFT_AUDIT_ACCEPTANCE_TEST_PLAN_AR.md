# SiteDocs — اختبارات القبول الإيجابية والسلبية لمصفوفة الصلاحيات P0
**الحالة:** migration مرشحة واختبارات قبول مضافة على فرع التطوير؛ جميع اختبارات قاعدة البيانات ما زالت NOT RUN لعدم توفر وصول إلى فرع Supabase معزول. قاعدة رؤية المسودة: المنشئ أو أي عضو من الطرف المنشئ، إضافة إلى مدير المشروع المعين صراحةً للقراءة الإشرافية.  
**الفرع:** `fix/cloudflare-workers-build-2026-11-13`  
**مصفوفة الصلاحيات:** `docs/security/ROLE_PERMISSION_MATRIX_DRAFT_CONFIDENTIALITY_AR.md`  
**نطاق:** P0-1 سرية المسودات وP0-2 عدم كشفها عبر سجل التدقيق، مع اختبار الحدود بين الأدوار الأربعة.

## 1. قواعد تنفيذ الاختبارات

- تنفذ فقط على قاعدة PostgreSQL/Supabase معزولة ومهيأة من snapshot/backup موثق؛ لا تستخدم قاعدة SiteDocs الحية.
- بيانات اصطناعية بالكامل، ومستخدم JWT مستقل لكل هوية. لا تستخدم service_role لاختبار صلاحيات المستخدمين.
- كل رفض يُختبر عبر المسار المباشر: PostgREST/SQL بدور authenticated، وRPC، وStorage API، وليس عبر إخفاء زر في الواجهة.
- يجب فحص عدم كشف وجود الوثيقة أو عددها أو عنوانها أو وصفها أو metadata أو اسم/مسار المرفق أو محتوى audit.
- تُسجل نتيجة كل حالة، وهوية المنفذ، وSHA للـ migration، وإصدار قاعدة الاختبار، وأي side effects.
- لا تعتبر المواصفات اختباراً منفذاً. الحالة الابتدائية لكل الحالات أدناه: **NOT RUN**.

## 2. بيانات الاختبار والهويات

ينشأ مشروعان تجريبيان منفصلان `P-A` و`P-B` وشركتان `C-A` و`C-B`، مع مستخدمين مستقلين:

| الرمز | الهوية/الدور | الإعداد |
|---|---|---|
| U-CR | منشئ الوثيقة | عضو في P-A؛ ينشئ D-DRAFT-A ويملك `created_by` |
| U-CR2 | منشئ آخر | عضو في P-A من طرف المنشئ نفسه أو طرف مختلف؛ ينشئ D-DRAFT-B |
| U-REV-NOW | المراجع الحالي | عضوية صريحة في P-A؛ طرفه يطابق `workflow_steps[current_step]` |
| U-REV-LATER | مراجع لاحق | عضو في P-A؛ طرفه موجود في خطوة لاحقة لا الحالية |
| U-PM | مدير المشروع | `project_members.is_project_manager=true` مع `project_role='viewer'`؛ ليس منشئ الوثيقة ولا المراجع الحالي |
| U-CO-ADMIN | مدير الشركة | `company_members.role='admin'` في C-A؛ دون تعيين مشروع أو دور PM |
| U-CO-OWNER | مالك الشركة | `company_members.role='owner'` في C-A؛ دون تعيين مشروع أو دور PM |
| U-OTHER | عضو طرف آخر | عضو P-A من طرف غير منشئ الوثيقة وغير الطرف الحالي |
| U-XTENANT | مستخدم مستأجر آخر | عضو P-B/C-B فقط، دون عضوية في P-A |
| U-ANON | مجهول | لا JWT authenticated |

تضيف migration المرشحة الحقل `project_members.is_project_manager` لتمثيل U-PM صراحةً؛ يجب تعيينه في fixture مع إبقاء `project_role='viewer'`. لا يُعاد تفسير `viewer` أو `pmc` تلقائياً على أنه PM.

## 7. اختبارات مباشرة لـ RPC والامتيازات

- RPC-01: استدعاء `transition_document` كـ U-PM أو مدير شركة دون تطابق الطرف — رفض.
- RPC-02: استدعاء RPC بمعرفات actor/project/document مزورة — الهوية تؤخذ من JWT والروابط يعاد التحقق منها.
- RPC-03: محاولة المنشئ الرد أو الاعتماد على وثيقته — رفض.
- RPC-04: فحص `EXECUTE` لكل `SECURITY DEFINER`: منع `PUBLIC` و`anon` عن RPCs الحساسة، والسماح لـ `authenticated` فقط حيث يلزم مع تحقق داخلي.
- RPC-05: استدعاء دوال داخلية غير مخصصة للعميل — رفض من ACL أو تحقق داخلي.
- RPC-06: اختبار أن صلاحية PM للقراءة لا تتسرب إلى دوال التعديل أو سير العمل.
- RPC-07: التحقق أن company owner/admin دون `project_members` لا يحصل على `project_role='admin'` ولا يستطيع استدعاء RPC المشروع.
- RPC-08: التحقق أن PM صريحاً لا يملك `can_manage_project`, `can_edit_documents`, `can_comment` رغم flag القراءة.

## 8. اختبارات عدم التراجع

- REG-01: تبقى صلاحيات الشركة محصورة في الشركة، ولا تتحول إلى دور مشروع عام.
- REG-02: لا تتغير استقلالية WIR وRFI في النماذج والترقيم والصلاحيات وسير العمل.
- REG-03: يبقى MQR في مسار المراجعة المستقل؛ لا تُفرض عليه رموز A/B/C/D/E/I افتراضياً.
- REG-04: عند استخدام الرد I في الأنواع التي ينطبق عليها، يغلق دورة المراجعة ويحفظ المستند في الأرشيف.
- REG-05: لا يكتسب مدير المشروع حق تعديل أو اعتماد نتيجة السماح له بقراءة المسودات.
- REG-06: لا يُسمح بقراءة عبر audit أو Storage أو RPC لما مُنع عبر documents RLS.
- REG-07: تبقى دفعات الاستيراد وصفوفها وسجلها محصورة بمنشئ الدفعة ومدير المشروع المخول.
- REG-08: OCR extraction يرث صلاحية قراءة الوثيقة المرتبطة بالمرفق.

## 10. بوابة النجاح

لا يُغلق P0-1 أو P0-2 إلا إذا:
1. اجتازت كل حالات السماح والمنع ذات الصلة.
2. لم يكشف أي مسار جانبي documents/revisions/reviews/comments/attachments/audit/Storage/RPC عن مسودة محمية.
3. اختبرت الأدوار بهويات JWT منفصلة، وليس service_role.
4. اجتازت حالات عزل المستأجرين.
5. تم حفظ نتائج قابلة لإعادة التشغيل مرتبطة بـ SHA محدد.
6. لا توجد حالة BLOCKED_SCHEMA مؤثرة على قرار الرؤية؛ يجب اختبار `is_project_manager` المستقل وإثبات عدم وراثة مدير الشركة لدور المشروع.

**الحالة الحالية:** أُعدت migration مرشحة وملفات اختبارات SQL/README في فرع التطوير. لم تُشغّل الاختبارات على PostgreSQL، ولم تُطبق migration على أي قاعدة بيانات أو Storage.
