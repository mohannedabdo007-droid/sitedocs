# تحليل فجوات التحكم في الوصول — SiteDocs

**التاريخ:** 2026-11-13  
**النطاق:** مراجعة المصدر + فحص قراءة فقط لقاعدة بيانات مشروع Lovable  
**الفرع:** `fix/cloudflare-workers-build-2026-11-13`  
**الحالة:** ثبتت فجوات فعلية في المصدر وقاعدة بيانات المشروع. لم تُعدّل قاعدة البيانات أو migrations ولم تُنفّذ اختبارات مستخدمين حقيقية.

## الخلاصة التنفيذية

التنفيذ الحالي لا يطابق قرارات الصلاحيات المعتمدة. توجد أربع فجوات مترابطة:

1. لا يوجد دور `project_manager` مستقل في enum `project_role` بقاعدة البيانات.
2. دالة `project_role_of` تحوّل عضوية مالك/مدير الشركة تلقائياً إلى دور مشروع `admin`، رغم اعتماد الفصل بين صلاحيات الشركة وصلاحيات المشروع.
3. دالة `transition_document` تمنح `admin` تجاوزاً لفحص الطرف المخوّل عند الإرسال وبدء المراجعة والرد/الإرجاع.
4. سياسات RLS للوثائق والإصدارات والمراجعات والمرفقات وStorage تسمح بالقراءة على أساس عضوية المشروع فقط، دون تطبيق حالة المسودة أو دور مدير المشروع المستقل.

هذه مخالفات تنفيذية وليست قرارات تصميم معلّقة. يجب تصحيحها قبل تفعيل دورة مستندية على بيانات عملاء حقيقية.

## الأدلة المؤكدة من ملفات المصدر

المرجع الأساسي: `drizzle/migrations/0000_core_schema.sql` و`0001_triggers_and_rpcs.sql` و`0002_storage_policies.sql`.

- enum `project_role` يحتوي فقط: `admin`, `controller`, `reviewer`, `viewer`؛ ولا يحتوي `project_manager`.
- `project_role_of` يرجع `admin` عند وجود عضوية شركة بدور `owner` أو `admin` حتى دون عضوية مشروع صريحة.
- `can_edit_documents` يسمح لـ`admin` و`controller`، ولذلك ينتقل أثر ترقية مدير الشركة إلى صلاحيات المشروع عبر الدالة السابقة.
- `transition_document` يسمح لـ`admin` بتجاوز مطابقة الطرف الحالي في `submit` و`start_review` و`respond` و`return`. هذا يخالف اشتراط أن تكون سلطة المراجعة مستقلة عن الإدارة وأن يصدر القرار من الطرف المعيّن.
- سياسات `documents` و`document_revisions` و`document_reviews` و`attachments` تعتمد `is_project_member(project_id)` فقط، ولا تفحص حالة المستند أو منشئه أو طرفه.
- سياسات `storage.objects` تسمح بقراءة ملفات bucket `document-files` لكل عضو مشروع. كون الـbucket خاصاً لا يعالج اتساع سياسة القراءة.
- سياسة التعليقات لا تربط القراءة بحالة المستند الأب؛ يلزم اختبارها ومعالجتها ضمن نفس نطاق الرؤية.

## ما تم التحقق منه في قاعدة بيانات مشروع Lovable

أُجريت استعلامات قراءة فقط على قاعدة البيانات المفعّلة لمشروع Lovable `Project Doc Control`:

- قاعدة البيانات متاحة وتعمل على PostgreSQL 17.11.
- ظهرت جداول المجال الأساسية، ومنها الشركات والمشاريع والوثائق والإصدارات والمراجعات والمرفقات وسجل التدقيق.
- ظهرت سياسات RLS الفعلية المذكورة أعلاه في `pg_policies`.
- ظهرت الدوال الفعلية `project_role_of` و`is_project_member` و`can_manage_project` و`can_edit_documents` و`can_comment` و`transition_document`، ومحتواها يؤكد فجوات تجاوز الإدارة وفحص الطرف.
- سجل `drizzle.__drizzle_migrations` يحتوي أربعة سجلات، وتطابق أوقات تطبيقها أوقات الإدخالات الأربعة في `drizzle/migrations/meta/_journal.json`. هذا تطابق في سجل التوقيت والترتيب، وليس إثباتاً مستقلاً لتطابق checksums لكل ملف migration.
- bucket `document-files` مستخدم في سياسات Storage؛ وسياسة القراءة الحالية قائمة على عضوية المشروع.

**حدود التحقق:** لم نثبت أن قاعدة Lovable هذه هي مشروع Supabase ذي المرجع `jezpyxuxjzxotxjykhky`؛ الربط المؤكد حالياً هو قاعدة البيانات المتاحة من داخل مشروع Lovable. كما لم ننفذ اختبارات JWT بمستخدمين منفصلين أو signed URL أو RPC مباشرة. بعد الاستعلامات السابقة وصلت أداة Lovable إلى حد استعلامات الخطة المجانية مؤقتاً، لذلك لم تُنفّذ استعلامات إضافية.

## التغييرات البرمجية غير المرتبطة بقاعدة البيانات

على فرع التطوير أضيفت قواعد domain واختبارات وحدات لتقريب الواجهة من القرارات المعتمدة:

- مدير المشروع ممثل كسلطة قراءة مستقلة، وليس كـ`admin`.
- مدير المشروع لا يحصل على إجراءات workflow أو إضافة إصدار من مجرد صلاحية القراءة.
- المسودة لا تظهر إلا لمنشئها أو عضو الطرف المنشئ، أو مدير المشروع للقراءة الإشرافية.
- لا تمنح عضوية الشركة وحدها وصولاً إلى المسودة دون عضوية مشروع صريحة.
- أزيل تجاوز `admin` لفحص الطرف المخوّل من `availableActions` في الواجهة.

**تنبيه أمني مهم:** هذه قواعد domain واختبارات وحدات فقط. لا تحل محل RLS أو RPC أو Storage، ولا تعني أن قاعدة البيانات أصبحت آمنة. دالة `transition_document` وسياسات RLS وStorage في قاعدة البيانات لم تتغير بعد.

## مراجعة صلاحيات تنفيذ الدوال

أظهر الفحص الساكن لملفات migrations أيضاً أن عدداً من الدوال يُنشأ بصلاحية التنفيذ الافتراضية لـ`PUBLIC`، ثم يقتصر السحب الصريح على `anon`. أمثلة ذلك RPCs في `0001_triggers_and_rpcs.sql` مثل `create_company` و`create_project` و`add_project_member` و`transition_document` و`commit_import_rows` و`preview_document_number`، وكذلك `add_company_member` و`save_import_validation` في `0003_import_validation_and_kpi_buckets.sql`.

سحب التنفيذ من `anon` وحده لا يلغي امتياز `PUBLIC` الافتراضي. يجب تدقيق كل دالة على حدة، وسحب `EXECUTE` من `PUBLIC` ثم منح أقل صلاحية لازمة صراحةً. لم تُنفّذ أي تغييرات على grants أو functions في قاعدة البيانات.

## متطلبات المعالجة على مستوى قاعدة البيانات

1. إضافة دور مشروع مستقل `project_manager` بمسار ترحيل آمن، وعدم استنتاجه من دور الشركة.
2. إزالة تحويل Company Owner/Admin تلقائياً إلى Project Admin؛ صلاحيات الشركة لا تمنح تلقائياً عضوية مشروع أو سلطة مراجعة.
3. جعل فحص الطرف المعيّن إلزامياً في الإرسال والمراجعة والرد والإرجاع، دون تجاوز إداري عام. تظل صلاحيات الإدارة منفصلة عن قرار الجهة الهندسية.
4. بناء شرط قراءة موحد للمستند: مدير المشروع يقرأ جميع مستندات المشروع للإشراف؛ بقية أعضاء المشروع لا يرون المسودة إلا إذا كانوا منشئها أو من الطرف المنشئ؛ وتطبق قواعد التوزيع المعتمدة بعد الإرسال.
5. تطبيق الشرط نفسه على الإصدارات والمراجعات والتعليقات والمرفقات، مع منع الوصول المباشر إلى الجداول التابعة.
6. ربط Storage object بسياسة المستند الأب، وعدم الاكتفاء بمعرفة project_id من مسار الملف عند إصدار signed URL أو القراءة.
7. مراجعة صلاحيات تنفيذ RPC ودوال SECURITY DEFINER، والتحقق من عدم وجود مسارات تتجاوز قواعد التفويض.
8. أخذ نسخة احتياطية قابلة للاستعادة وتنفيذ تجربة استعادة قبل أي تغيير، ثم اختبار الترحيل على بيئة غير إنتاجية.

## مصفوفة اختبارات القبول المطلوبة

| السيناريو | النتيجة المطلوبة |
|---|---|
| منشئ المسودة يقرأها | سماح وفق عضويته وصلاحياته |
| عضو من الطرف المنشئ يقرأ المسودة | سماح |
| عضو من طرف آخر يقرأ مسودة غير مرسلة | رفض/عدم ظهور الصف |
| مدير المشروع يقرأ المسودة | سماح للقراءة فقط |
| مدير المشروع يحاول تعديل/إرسال/مراجعة/رد/إغلاق | رفض ما لم يكن مخولاً بشكل مستقل بدور آخر |
| Company Admin بلا عضوية مشروع يحاول القراءة أو التعديل | رفض |
| Project Admin ليس الطرف المعيّن يحاول الرد أو الاعتماد | رفض |
| عضو غير مخول يستعلم عن إصدار أو مراجعة أو تعليق لمسودة | رفض |
| عضو غير مخول يقرأ مرفق مسودة أو ينشئ signed URL | رفض |
| عضو مشروع يقرأ وثيقة مرسلة | سماح وفق نطاق التوزيع المعتمد |
| مستخدم من شركة أخرى يستعلم عن أي سجل | لا تظهر أي بيانات خارج tenant |
| مستخدم يستدعي RPC مباشرة | يطبق الخادم نفس الدور والطرف والحالة |
| Storage object path مباشر | يخضع لنفس صلاحية المستند الأب |

يجب تنفيذ الاختبارات بمستخدمين فعليين منفصلين وببيانات اختبار غير إنتاجية، مع التحقق من الاستعلامات المباشرة وRPC وStorage.

## ضوابط التغيير

- لم يتم تعديل أي جدول أو policy أو function أو migration في قاعدة البيانات.
- لم يتم تنفيذ backup أو restore؛ لا ندّعي وجود نسخة احتياطية.
- لم يتم النشر إلى الإنتاج أو الدمج إلى `main`.
- لا تُنفّذ تغييرات قاعدة البيانات قبل إثبات مرجع قاعدة البيانات المقصودة، والتحقق من النسخ الاحتياطي والاستعادة، والحصول على الموافقة الصريحة المطلوبة.

## القرار التنفيذي

تظل جاهزية الأمان متعدد الأطراف **غير مجتازة** حتى تنفيذ معالجة RLS/RPC/Storage واجتياز اختبارات العزل الحية. يمكن مواصلة تطوير domain والواجهات والاختبارات على فرع التطوير، لكن لا يجوز اعتبار قواعد domain وحدها حماية أمنية.
