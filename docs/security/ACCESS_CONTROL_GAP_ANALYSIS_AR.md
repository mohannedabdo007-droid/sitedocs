# تحليل فجوات التحكم في الوصول — SiteDocs

**التاريخ:** 2026-11-13  
**النطاق:** مراجعة ساكنة لسياسات RLS ودوال الصلاحيات في فرع التطوير  
**الفرع:** `fix/cloudflare-workers-build-2026-11-13`  
**الحالة:** نتائج مراجعة مؤكدة من ملفات المصدر؛ لم تُنفّذ اختبارات RLS الحية.

## الخلاصة التنفيذية

لا يجوز اعتبار عزل المسودات بين أطراف المشروع محققاً حالياً. سياسة القراءة الحالية للوثائق تمنح كل عضو مشروع حق قراءة جميع الوثائق دون استثناء حالة المسودة. كما تمنح سياسات القراءة في جداول الإصدارات والمراجعات والمرفقات حق القراءة لكل أعضاء المشروع. هذا يتعارض مع قرار المنتج: المسودات لا تظهر للأطراف الأخرى قبل الإرسال، ومدير المشروع يستطيع الاطلاع عليها للإشراف دون اكتساب صلاحية تعديلها أو مراجعتها أو اعتمادها.

**التصنيف:** مانع أمني قبل التشغيل ببيانات حقيقية أو تقديم ضمانات عزل للعملاء.

## الأدلة في المصدر

المرجع: `drizzle/migrations/0000_core_schema.sql`

| الجدول | السياسة الحالية | الأثر |
|---|---|---|
| `documents` | `documents: members read` باستخدام `is_project_member(project_id)` | كل عضو مشروع يستطيع قراءة المسودات، وليس مدير المشروع فقط |
| `document_revisions` | `revisions: members read` باستخدام `is_project_member(project_id)` | يمكن قراءة تفاصيل الإصدارات المرتبطة بالمسودات |
| `document_reviews` | `reviews: members read` باستخدام `is_project_member(project_id)` | سجل المراجعات متاح لكل أعضاء المشروع |
| `attachments` | `attachments: members read` باستخدام `is_project_member(project_id)` | بيانات المرفقات قابلة للقراءة لكل أعضاء المشروع |

وتُعرّف الدالة `is_project_member` العضوية عبر `project_role_of`، ولا تفحص حالة المستند أو طرفه أو ما إذا كان مسودة.

## ما لا تثبته هذه المراجعة

- لم يتم الاتصال بقاعدة Supabase الحية لاختبار السياسات.
- لم يتم إثبات ما إذا كانت قاعدة Lovable الحالية تطابق تماماً ملفات migrations الموجودة في GitHub.
- لم يتم اختبار signed URLs أو الوصول المباشر إلى Storage objects.
- لم يتم إجراء اختبار مستخدمين من شركتين أو طرفين مختلفين.
- نجاح lint والاختبارات والبناء لا يثبت صحة RLS أو العزل متعدد الشركات.

## متطلبات المعالجة

1. تعريف سياسة واضحة لرؤية المسودة: منشئها/الطرف المخوّل ومدير المشروع لأغراض الإشراف فقط، وفق صلاحية قراءة صريحة.
2. يجب ألا تتحول صلاحية مدير المشروع للقراءة إلى صلاحية تعديل أو إرسال أو بدء مراجعة أو الرد أو الإغلاق.
3. تطبيق اتساق الرؤية على الوثيقة وإصداراتها ومرفقاتها وسجل مراجعاتها، لا على جدول `documents` وحده.
4. منع التحايل بالاستعلام المباشر عن الجداول التابعة أو بمسارات Storage.
5. الإبقاء على RFI منفصلاً عن WIR، وعلى MQR بمسار مستقل دون رموز رد عامة افتراضياً.
6. تنفيذ التعديل عبر مسار إدارة قاعدة البيانات المعتمد في Lovable؛ لا تُعدّل migrations أو مخطط قاعدة البيانات من هذا المستودع لأن تعليمات المشروع تنص على أن Lovable هو مالك تغييرات قاعدة البيانات.
7. أخذ نسخة احتياطية وخطة استعادة قبل أي تغيير على قاعدة البيانات.

## مصفوفة اختبارات القبول المطلوبة

| السيناريو | النتيجة المطلوبة |
|---|---|
| منشئ المسودة يقرأها | سماح وفق صلاحية المشروع |
| عضو من طرف آخر يقرأ مسودة غير مرسلة | رفض/عدم ظهور الصف |
| مدير المشروع يقرأ المسودة للإشراف | سماح للقراءة فقط |
| مدير المشروع يحاول تعديل المسودة | رفض |
| مدير المشروع يحاول اعتمادها أو الرد عليها | رفض ما لم يكن مخولاً مستقلاً بصفة مراجِع صحيحة |
| عضو غير مخول يستعلم عن إصدار مسودة مباشرة | رفض/عدم ظهور الصف |
| عضو غير مخول يقرأ مرفق مسودة أو ينشئ signed URL | رفض |
| عضو مشروع يقرأ وثيقة مرسلة ومصرحاً بها | سماح حسب نطاق الطرف ومسار التوزيع |
| مستخدم من شركة أخرى يستعلم عن أي سجل | لا تظهر أي بيانات خارج tenant |
| مستخدم يحاول استدعاء RPC مباشرة | يطبق الخادم نفس قواعد الدور والطرف والحالة |

يجب تنفيذ الاختبارات بمستخدمين فعليين منفصلين وببيانات اختبار غير إنتاجية، مع التحقق من نتائج الاستعلامات المباشرة ومحاولات RPC وStorage.

## القرار

**إيقاف اعتماد جاهزية الأمان متعدد الأطراف مؤقتاً.** يمكن مواصلة تطوير واجهات القراءة ومسارات العمل على فرع التطوير، لكن لا تُفعّل عمليات إنشاء/إرسال/مراجعة مستندات على بيانات حقيقية ولا يُعلن اجتياز RLS حتى تُعالج الفجوات ويُنفّذ اختبار عزل حي موثق.

لم يتم في هذه المراجعة تعديل أي migration أو schema أو قاعدة بيانات أو فرع إنتاج.
