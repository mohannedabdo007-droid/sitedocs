# SiteDocs — نموذج الشركات والهوية والتفويض

**الحالة:** تصميم مقترح للتنفيذ بعد تثبيت قاعدة البيانات الصحيحة  
**النطاق:** Core متعدد الشركات والمشاريع  
**القرار:** لا تُنفذ أي migration أو كتابة قاعدة بيانات اعتماداً على هذا المستند وحده.

## 1. المبادئ الملزمة

1. كل بيانات العميل التشغيلية مملوكة لشركة (Tenant) محددة.
2. المشروع يتبع شركة واحدة في النسخة الأساسية؛ مشاركة مشروع بين شركات مختلفة تحتاج علاقة مشاركة صريحة ومحدودة، ولا تُستنتج من العضوية العامة.
3. هوية المستخدم مستقلة عن عضويته في الشركة أو المشروع.
4. المصادقة تثبت هوية المستخدم، أما التفويض فيثبت حقه في تنفيذ الإجراء على المورد المحدد.
5. المنع هو الوضع الافتراضي: لا صلاحية ما لم توجد عضوية وصلاحية صريحة.
6. لا تمنح صلاحية الاطلاع على المسودات حق تعديلها أو مراجعتها أو اعتمادها.
7. كل قرار مراجعة أو اعتماد أو تغيير صلاحية حساس يجب أن ينتج حدث تدقيق.

## 2. الكيانات الأساسية المقترحة

| الكيان | الغرض | القيود الأساسية |
|---|---|---|
| companies | سجل الشركات المستأجرة | معرف ثابت، حالة، إعدادات ومرجع ترخيص |
| user_profiles | بيانات التطبيق المرتبطة بهوية Auth | المفتاح يطابق Auth user id؛ لا تخزن كلمات مرور |
| company_memberships | عضوية المستخدم في الشركة | unique(company_id, user_id)، حالة العضوية |
| company_roles | تعريف الأدوار على مستوى الشركة | أدوار إدارية لا تمنح تلقائياً صلاحيات المشروع |
| projects | المشاريع | company_id إلزامي، رقم مشروع فريد داخل الشركة |
| project_memberships | عضوية المستخدم في مشروع | unique(project_id, user_id)، حالة ودور |
| project_roles | أدوار المشروع | مثل admin/controller/reviewer/viewer مع صلاحيات منفصلة |
| permissions | مفاتيح صلاحيات ذرية | أسماء ثابتة مرتبطة بموارد وأفعال |
| role_permissions | ربط الدور بالصلاحيات | unique(role_id, permission_id) |
| audit_events | سجل الأحداث الحساسة | append-only للمستخدمين العاديين، مع actor وtenant وresource وaction ووقت |

هذه قائمة منطقية وليست تأكيداً بأن جداول مماثلة غير موجودة حالياً. يجب فحص المخطط الفعلي أولاً وتجنب تكرار الكيانات أو إسقاط بيانات قائمة.

## 3. نموذج التفويض

تُقيّم كل عملية خادمية وفق التسلسل التالي:

1. التحقق من جلسة المستخدم ورمز الوصول.
2. استخراج هوية المستخدم من claims موثوقة، لا من حقول يرسلها المتصفح.
3. تحديد الشركة والمشروع من المورد المطلوب والتحقق من ارتباطهما.
4. التحقق من أن عضوية المستخدم في الشركة والمشروع نشطة.
5. التحقق من صلاحية الفعل المحدد على نوع المورد وحالته.
6. التحقق من قيود فصل الواجبات، مثل منع المنشئ من اعتماد معاملته.
7. تنفيذ العملية ضمن سياق آمن وإضافة حدث تدقيق مناسب.

لا تعتبر قيمة company_id أو project_id القادمة من الواجهة دليلاً على الاستحقاق. يجب إعادة التحقق منها خادمياً وربطها بالمورد الفعلي.

## 4. حدود الأدوار

- **Company Owner/Admin:** إدارة الشركة وعضوياتها وإعداداتها؛ لا يحصل تلقائياً على قرار اعتماد هندسي داخل مشروع.
- **Project Admin:** إدارة إعدادات وعضويات المشروع ضمن حدود الشركة؛ لا يتجاوز صلاحيات الجهات المخولة بالمراجعة والاعتماد.
- **Document Controller:** إدارة التسجيل والتوزيع والمتابعة وفق الصلاحيات المعينة؛ لا يعتمد المحتوى الهندسي لمجرد كونه ضابط وثائق.
- **Reviewer:** مراجعة الأنواع والمراحل المسندة إليه فقط.
- **Viewer:** قراءة النطاق المسموح به دون أي عمليات تغيير.
- **Project Manager:** قد يرى المسودات لأغراض الإشراف إذا مُنح ذلك صراحة؛ الاطلاع لا يبيح التعديل أو إصدار قرار نيابة عن المراجع/المعتمد المخول.

الأدوار أسماء تجميعية. القرار الفعلي يجب أن يعتمد على صلاحيات ذرية مثل:
- `project.read`
- `project.members.manage`
- `document.read`
- `document.draft.read`
- `document.create`
- `document.submit`
- `document.review.start`
- `document.review.respond`
- `document.return`
- `document.approve`
- `document.distribute`
- `audit.read`

## 5. عزل البيانات وRLS

- تفعيل RLS على كل جدول مكشوف عبر Data API.
- سياسات SELECT وINSERT وUPDATE وDELETE تُكتب لكل عملية حسب نموذج التفويض؛ لا تستخدم سياسة عامة واحدة لكل الجداول.
- UPDATE يتطلب سياسة قراءة متوافقة وسياسة WITH CHECK تمنع نقل السجل إلى tenant آخر.
- المفاتيح الخارجية والقيود المركبة يجب أن تمنع ربط سجل تابع لشركة بمشروع شركة أخرى.
- لا تعتمد على إخفاء عناصر الواجهة أو فلترة React كحد أمني.
- لا تستخدم user_metadata كمصدر لصلاحيات أو أدوار.
- تجنب SECURITY DEFINER لمعالجة أخطاء الصلاحيات؛ أي استثناء منه يحتاج مبرراً ومراجعة مستقلة.
- لا تستخدم Service Role في عمليات المستخدم اليومية؛ فهو يتجاوز RLS ويقتصر على مهام خادمية ضيقة ومراجعة.

## 6. فصل الواجبات وسجل التدقيق

يجب أن يميز النظام بين منشئ المعاملة ومقدمها ومراجعها ومعتمدها ومنفذ الدفع. يمنع التطابق بين المنشئ والمعتمد أو منفذ الدفع افتراضياً، وأي استثناء يكون بسياسة موثقة وموافقة مستقلة وأثر تدقيق.

يتضمن الحد الأدنى لحدث التدقيق:
- tenant_id وproject_id عند انطباقهما
- actor_user_id
- action وresource_type وresource_id
- timestamp
- نتيجة العملية
- سبب أو تعليق عند الحاجة
- request/correlation id
- القيم السابقة واللاحقة للحقول الحساسة وفق سياسة تقليل البيانات

يجب منع المستخدم العادي من تعديل أو حذف سجل التدقيق.

## 7. اختبارات القبول الإلزامية

1. مستخدم الشركة A لا يقرأ أو يعدل سجل الشركة B حتى عند تبديل UUID يدوياً.
2. مستخدم الشركة A لا يفتح مشروعاً تابعاً للشركة B.
3. مستخدم غير عضو في المشروع لا يقرأ مستنداته حتى لو كان عضواً في الشركة.
4. Viewer لا ينفذ mutation عبر الواجهة أو استدعاء الخادم مباشرة.
5. مدير المشروع لا يعدل مسودة لمجرد امتلاكه صلاحية الاطلاع عليها.
6. مدير المشروع لا يصدر قرار مراجعة أو اعتماد نيابة عن جهة غير مخول بها.
7. WIR وRFI يطبقان صلاحيات ومسارات مستقلة.
8. منشئ المعاملة لا يعتمدها ولا ينفذ صرفها افتراضياً.
9. تغيير الدور أو العضوية يسجل في Audit Trail.
10. لا يستطيع المستخدم تعديل tenant_id أو project_id لنقل المورد إلى نطاق آخر.

يجب تنفيذ الاختبارات على قاعدة اختبارية ببيانات لشركتين على الأقل، مع حالات سماح ومنع لكل عملية حساسة.

## 8. ترتيب التنفيذ

1. قراءة مخطط Supabase الفعلي وRLS والسياسات والمفاتيح الخارجية.
2. مقارنة الكيانات القائمة بهذا النموذج وتحديد الفجوات فقط.
3. إعداد ERD نهائي وقرارات ADR للحقول والقيود.
4. مراجعة خطة migration ونسخة احتياطية قابلة للاستعادة.
5. تنفيذ migrations على بيئة اختبارية فقط بعد موافقة صريحة.
6. تشغيل اختبارات العزل والتفويض وسجل التدقيق.
7. طلب موافقة مستقلة قبل أي ترحيل لبيانات فعلية أو نشر إنتاجي.

## 9. ما لم يُنفذ

هذا المستند تصميم معماري فقط. لم تُنشأ جداول أو سياسات RLS، ولم تُعدل قاعدة بيانات، ولم تُشغّل اختبارات أو build. ولا يحل محل التحقق من المشروع ذي المرجع الصحيح في Supabase.
