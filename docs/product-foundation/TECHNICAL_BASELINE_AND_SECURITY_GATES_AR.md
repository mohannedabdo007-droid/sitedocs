# المراجعة التقنية وخطوط الأمان الأساسية

**تاريخ المراجعة:** 13 نوفمبر 2026  
**الفرع:** `fix/cloudflare-workers-build-2026-11-13`  
**نطاق المراجعة:** قراءة ملفات المستودع فقط. لم يتم الاتصال بقاعدة البيانات أو تعديلها، ولم يتم تشغيل build أو tests من خلال GitHub.

## 1. النتيجة التنفيذية

المستودع يحتوي أساساً تقنياً أولياً جيداً في بعض الجوانب، لكنه ليس بعد نظام ضبط وثائق متعدد الشركات جاهزاً للاستخدام التشغيلي. توجد واجهة Dashboard تجريبية، ومكتبة قواعد Workflow، وعميل Supabase، وطبقة تحقق من JWT داخل server functions. لكن لا توجد في شجرة المسارات الحالية إلا الصفحة الرئيسية، وملف Drizzle schema فارغ، ولا يوجد إثبات من هذه المراجعة أن مخطط قاعدة البيانات الفعلي يطابق أنواع TypeScript أو migrations.

**قرار المراجعة:** لا ننشئ أو نفعّل تسجيل دخول تشغيلياً، ولا نضيف استعلامات بيانات أو migrations، قبل إثبات هوية مشروع Supabase الصحيح ومطابقة مخططه.

## 2. ما وجدناه في الكود

| المجال | الموجود فعلياً | التقييم |
|---|---|---|
| Routing | `/` فقط في `src/routeTree.gen.ts` | لا توجد صفحات مستقلة للوحدات أو الدخول |
| Dashboard | بيانات ثابتة في `src/lib/dashboard-summary.ts` وواجهة في `src/routes/index.tsx` | معاينة تصميمية، وليست مؤشرات حية |
| Document Register | أنواع وفلترة في `src/lib/document-register.ts` | لا يثبت وجود حفظ أو قراءة فعلية من DB |
| Supabase client | `client.ts` يقرأ Vite/Worker environment variables | يتوقف عند غياب الإعدادات |
| Browser session | `previewAuthStorage.ts` يدعم localStorage ووسيط Lovable Preview | تخزين جلسة، وليس نظام هوية أو صلاحيات |
| Token attachment | `auth-attacher.ts` يضيف Bearer token إلى server functions | تمرير اعتماد الجلسة فقط |
| Server auth | `auth-middleware.ts` يتحقق من claims ووجود `sub` | لا يثبت وحده عضوية الشركة أو المشروع أو الدور |
| Admin client | `client.server.ts` يستخدم Service Role ويتجاوز RLS | سطح عالي الحساسية؛ يمنع استخدامه في مسارات المستخدم العادية |
| Domain rules | `src/lib/domain.ts` يحتوي دورة مستند وإجراءات أساسية | قواعد أولية تحتاج اختباراً وتوحيداً مع DB |
| Database schema | `drizzle/schema.ts` فارغ | لا يوجد تعريف Drizzle معتمد |
| Tests | توجد اختبارات domain وimport وKPI وrouting | وجود الاختبارات لا يعني أنها نُفذت أو نجحت |

## 3. موانع الإطلاق

### 3.1 تحديد قاعدة البيانات

ملف `supabase/config.toml` يشير إلى project ref هو `jezpyxuxjzxotxjykhky`. لا يجوز افتراض أن أي مشروع آخر ظاهر في الحساب الموصول هو قاعدة البيانات المقصودة. قبل أي تغيير يلزم إثبات التطابق من مصدر موثوق وموافقة صاحب المشروع على الكتابة عند الحاجة.

### 3.2 فصل المصادقة عن التفويض

التحقق من JWT يجيب عن سؤال: «هل هذا رمز صالح وله مستخدم؟». لكنه لا يجيب عن:
- هل المستخدم عضو في الشركة الحالية؟
- هل الشركة تملك المشروع المطلوب؟
- هل لديه دور على هذا المشروع؟
- هل يسمح له هذا الدور بتنفيذ الإجراء المحدد على هذا المستند؟
- هل هو الطرف الحالي المخوّل بالمراجعة؟

يجب أن يتحقق كل server function من tenant membership وproject membership وpermission على الخادم، وألا يعتمد على إخفاء عناصر الواجهة أو بيانات يرسلها المتصفح.

### 3.3 عزل الشركات (Tenant Isolation)

قبل إدخال بيانات حقيقية، يجب أن تحمل الجداول التشغيلية نطاق الشركة `company_id`، وأن ترتبط المشاريع بالشركة، وأن تُفرض قيود العزل على مستوى قاعدة البيانات باستخدام RLS وسياسات موثقة ومختبرة. لا يكفي تمرير `company_id` من العميل أو فلترة النتائج في React.

### 3.4 مفاتيح الخدمة

`SUPABASE_SERVICE_ROLE_KEY` يتجاوز RLS. يجب ألا يصل إلى حزمة المتصفح، أو ملفات route مشتركة، أو سجلات الأخطاء. يقتصر استخدامه على عمليات خادم محددة ومراجعة، مع فحوص تفويض صريحة وسجل تدقيق. الأفضل استخدام صلاحيات المستخدم وRLS في العمليات اليومية.

### 3.5 الأسرار والبيئات

يلزم فصل إعدادات Preview وDevelopment وProduction، ومنع تضمين مفاتيح الخدمة في متغيرات `VITE_*` أو أي متغير يُضمّن في المتصفح، والتحقق من المتغيرات المطلوبة عند بدء الخدمة برسائل لا تكشف قيمة الأسرار.

## 4. ترتيب التنفيذ الآمن

1. **تثبيت مرجع قاعدة البيانات:** إثبات project ref المقصود، ثم قراءة schema وRLS والسياسات الحالية فقط.
2. **تصميم نموذج الهوية متعدد الشركات:** شركات، عضويات، مستخدمون، مشاريع، عضويات المشاريع، أدوار وصلاحيات.
3. **تأسيس العزل:** مفاتيح خارجية وقيود uniqueness وRLS واختبارات تمنع القراءة والكتابة بين شركتين.
4. **تأسيس المصادقة:** تسجيل الدخول، الخروج، استعادة كلمة المرور، التحقق من البريد، MFA حسب السياسة، وحماية الجلسات.
5. **تأسيس التفويض:** فحوص خادمية لكل عملية، مع اختبارات deny-by-default.
6. **تأسيس Document Core:** سجل المستند، الإصدارات، الملفات، التوزيع، وسجل التدقيق، ثم ربط WIR وRFI بمسارين منفصلين.
7. **التحقق:** تشغيل lint وtypecheck/build والاختبارات، ثم اختبارات أمنية لعزل الشركات قبل نشر Preview قابل للاختبار.
8. **الإطلاق:** لا دمج إلى `main` ولا نشر إنتاجي إلا بموافقة مستقلة.

## 5. بوابة القبول لنموذج الشركات والصلاحيات

لا تعتبر هذه المرحلة مكتملة حتى تنجح الحالات التالية على قاعدة بيانات اختبارية:
- مستخدم الشركة A لا يستطيع قراءة أو تعديل أي سجل تابع للشركة B حتى عند تغيير UUID يدوياً.
- مستخدم الشركة A لا يستطيع فتح مشروع لا يملك عضوية فيه.
- Viewer لا يستطيع تنفيذ أي mutation حتى لو استدعى server function مباشرة.
- صلاحية مدير المشروع في الاطلاع على المسودات لا تمنحه حق تعديلها أو إصدار قرار مراجعة نيابة عن الجهة المخولة.
- المستخدم لا يستطيع اعتماد أو صرف معاملة أنشأها بنفسه إلا باستثناء موثق ومصرح به.
- كل تغيير حالة أو صلاحية ينتج Audit event غير قابل للتعديل من المستخدم العادي.
- طلبات WIR وRFI لا تشترك في دورة مراجعة واحدة أو صلاحيات مختلطة.

## 6. حدود هذه المراجعة

هذه وثيقة تدقيق مبنية على قراءة ملفات الفرع فقط. لم يتم:
- الاتصال بقاعدة Supabase أو التحقق من project ref عبر بيئة تشغيل.
- تنفيذ SQL أو migrations أو أي كتابة في قاعدة البيانات.
- تشغيل `npm test` أو `npm run build` أو `npm run lint`.
- إنشاء واجهة دخول توحي بوجود مصادقة فعالة.
- دمج الفرع أو النشر إلى الإنتاج.

**الخلاصة:** الأولوية ليست إضافة شاشة Login شكلية؛ الأولوية إثبات قاعدة البيانات الصحيحة ثم بناء عزل الشركات والتفويض على الخادم وقاعدة البيانات. هذا هو الأساس الذي يمنع تسرب بيانات العملاء ويجعل SiteDocs منتجاً تجارياً قابلاً للاعتماد.
