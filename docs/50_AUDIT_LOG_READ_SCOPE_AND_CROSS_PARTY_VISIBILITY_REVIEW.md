## 2. Executive summary

The audit-log SELECT policy allows an authenticated user to read a row when either:
- the row has a non-null `project_id` and `is_project_member(project_id)` returns true; or
- the row has a null `project_id`, a non-null `company_id`, and the user is a company admin.

The helper `is_project_member()` checks whether `project_role_of()` is non-null. The role helper accepts a direct project membership or company owner/admin membership for the project's company. The audit policy does not further filter project-scoped audit rows by project party, event entity type, or event sensitivity.

This is broader than a role-specific audit view. It may be intentional for project-wide transparency, but it creates a cross-party visibility question that must be resolved against the approved external-party access model.

## 3. Finding

### F50-01 — Project-scoped audit entries are readable by every project member without event- or party-level filtering

**Severity:** Medium — potential cross-party information exposure; requires role-based verification

**Evidence:**
1. The policy `audit: project members read` permits SELECT when `project_id is not null and public.is_project_member(project_id)`.
2. `is_project_member()` returns whether `project_role_of()` is non-null; it does not inspect the caller's party for audit visibility.
3. `project_role_of()` resolves a direct project membership role or grants the project admin role to company owners/admins for the parent company's project.
4. The audit trigger writes changes for companies, company members, projects, project members, response codes, workflows, numbering schemes, documents, revisions, attachments, comments, and import batches.
5. The audit policy does not constrain `entity_type`, `action`, or fields inside `changes` based on the caller's party/role.

**Potential impact:**
- A reviewer or external project party may be able to read project-scoped audit events generated by another party or an internal controller, depending on the actual project membership configuration.
- Audit diffs may contain internal configuration or operational metadata not intended for every external project member.
- A company/project role may have broader audit visibility than its access to the underlying document or workflow details would suggest.
- Company-level events with null `project_id` are separately restricted to company admins, but this does not narrow project-scoped events.

**Important qualification:** The migration does not prove that a real user's membership configuration exposes confidential information. The finding identifies a broad policy condition and the need to verify it against intended business permissions.

## 4. Recommended verification and remediation direction (not implemented)

1. Define an audit visibility matrix for company owner/admin, project admin, document controller, reviewer, contractor, consultant, and other external parties.
2. Classify audit events by sensitivity: document lifecycle, workflow configuration, membership/role changes, numbering settings, import metadata, attachment metadata, and company administration.
3. Test with at least two different parties in the same project and with a company admin, using real authenticated sessions or an isolated test database.
4. Confirm that a party sees only the audit events and fields allowed by the approved project/company scope; do not infer visibility solely from the current UI.
5. If broad project membership visibility is not intended, replace the single broad rule with explicit role/party-aware policy or a restricted audit view/RPC that returns only approved event fields.
6. Apply field-level minimization to `changes`; avoid exposing raw spreadsheet values, internal notes, private configuration, or sensitive error details.
7. Preserve the special company-level restriction for rows without a project scope unless a separately approved policy says otherwise.
8. Add automated RLS tests for cross-project isolation, cross-company isolation, same-project cross-party access, company admins, removed members, and null-project audit entries.
9. Keep audit read permission separate from document edit, workflow action, and administrative privileges.

## 5. Required security test matrix

| Caller | Event scope | Expected verification |
|---|---|---|
| Project member / reviewer | Same project, own party | Confirm allowed event and field subset |
| Project member / reviewer | Same project, another party | Confirm no unintended internal or restricted data |
| Project controller | Same project | Confirm approved operational audit visibility |
| Company owner/admin | Projects in own company | Confirm intended company-wide visibility |
| Member of another project | Different project | Must not read the event |
| Member of another company | Different company | Must not read the event |
| Non-admin | Null-project company event | Must not read under the current stated policy |
| Removed project member | Previously accessible project | Must lose access according to current membership state |

The expected result for same-project cross-party access must be decided by the approved product policy before the test is treated as pass/fail.

## 7. Conclusion

The checked-in RLS policy grants project-wide audit-log reads to any user recognized as a project member, with no additional event-type or party-level filter. This may be intentional, but it must be validated against the product's external-party confidentiality rules. Run a role-by-role RLS test matrix and narrow the policy only if the approved access model requires it.
